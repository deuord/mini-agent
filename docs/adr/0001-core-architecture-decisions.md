# ADR-0001 核心架构决策

日期：2026-09-26
状态：已接受

本文记录 mini-agent 的三个核心架构决策及理由。

## 决策 1：Web 端用 WebSocket 而非 SSE

**背景**：agent 的对话是双向的，不仅后端要流式推 token 给前端，前端还要回传用户输入（对话消息、命令确认、ask_user 回答、停止信号）。

**决策**：用 WebSocket 作为前后端通信协议。

**理由**：

- 双向：SSE 是单向（服务端到客户端），用户确认 / 提问回答 / 停止需要额外 HTTP 通道或第二个连接，状态管理更复杂。
- 单连接：一个 WS 连接承载「流式 token + 工具调用事件 + 确认问答 + 停止」全生命周期，session 状态天然绑定连接。
- 生态成熟：FastAPI 原生支持，uvicorn 稳定。

**代价**：WS 状态管理比无状态 HTTP 复杂，需处理断线重连；对纯「一次性问答」场景略重。可接受。

## 决策 2：向量存储用 sqlite-vec 而非 Chroma / pgvector

**背景**：RAG 与长期记忆需要向量检索。候选有 Chroma（独立服务）、pgvector（需 PostgreSQL）、sqlite-vec（SQLite 扩展）。

**决策**：sqlite-vec。

**理由**：

- 与现有架构一致：项目已用 SQLite 存最近访问和 Session，sqlite-vec 复用同一个单文件存储心智，零服务、零运维。
- clone 即用：Chroma / pgvector 需要额外起服务或装数据库，破坏「桌面单机、开箱即用」定位。
- 体积小：SQLite 扩展，安装成本低，适合桌面分发。

**代价**：极端规模（亿级向量）性能弱于专用向量库；本项目是单用户桌面助手，量级远未到瓶颈。可接受。

## 决策 3：runner 保持传输无关

**背景**：项目要支持 CLI / Web / 桌面三端。

**决策**：agent 核心（runner）只产出事件流，不 print、不碰 WebSocket；三端各自实现 renderer 消费事件流，需要回传时注入回调（confirm / ask_user / cancel）。

**理由**：

- 复用：三端共用同一套 ReAct 循环，新增端只写 renderer，不改核心。
- 可测：核心逻辑不依赖 IO 通道，单测直接消费事件流断言。
- 可扩展：未来加 Tauri 桌面壳，内嵌 Web 前端即可，无需改动后端。

**代价**：多一层事件流抽象，早期略显「重」。但三端是明确目标，收益远大于成本。
