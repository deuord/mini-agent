# ADR-0002 Web 端改用 HTTP + SSE，废止 WebSocket

日期：2026-09-29
状态：已接受（废止 ADR-0001 决策 1）

本文记录一次传输选型的纠偏：ADR-0001 决策 1 选了 WebSocket，理由是「确认 / 提问需要双向通信」；该理由不成立，v2.1 改为 HTTP + SSE。

## 决策：Web 端用 HTTP + SSE，确认 / 提问走「回合断点 + 新请求续跑」

**背景**：v2.1 要加命令确认（用户点 y/n 才执行）和 ask_user（Agent 反问）。ADR-0001 决策 1 据此认定需要 WebSocket。动手前按「避免过度设计、优先简单经典方案」这条原则逐条复审，发现该结论建立在两个错误前提上（见下文复盘）。

**决策**：

- 流式输出用 HTTP + SSE（`StreamingResponse` + `text/event-stream`）：`POST /api/chat` 发消息，`POST /api/chat/resume` 提交对确认 / 提问的回答
- runner 遇确认 / 提问时把断点写进 `session.pending` 并**结束本段**（yield 事件，绝不挂起等回答）——回合状态不寄生在连接上
- 断点以 `tool_call_id` 作关联键；用户回答后由新的一次请求续跑（`resume_turn`）
- 原 `/api/chat/stream` WebSocket 端点删除

**理由**：

- 需求认错了：真正的需求不是「长连接」，而是「记下回合跑到哪 + 下次请求接着跑」，与连接长短无关。
- 「用户此刻就在等的输入」不等于「服务端主动推」：确认 / 提问是用户盯着屏幕发起的一次多轮请求，天然可由新请求承载。
- 业界一致：OpenAI Assistants（`Run.status → requires_action → submit_tool_outputs`）、LangGraph（`interrupt` + checkpoint + 同 `thread_id` 重新 invoke）、Eino（interrupt / resume）、MCP elicitation（Streamable HTTP，官方 spec 明确不引入长连接）。
- 白拿 HTTP 全家桶：CDN / 网关 / 鉴权 / 限流 / 重试 / 负载均衡，不需要粘性会话、心跳、重连、多实例广播。
- 连接可断可换：断点存服务端，重连 / 换浏览器 / 换端都能接着答——WS 版做不到。
- 白捡的简化：原为「等确认时还要能收新消息」而设计的「统一输入通道（常驻读线程 + queue + 状态分发）」不再需要，CLI 变成朴素的一问一答。

**代价**：

- 服务端要承担断点的一致性：未配对的 `tool_call` 必须补占位结果（否则下次请求 400）、`tool_call_id` 防串号与重放、断点一次性消费防重复提交。
- 前端不能用 `EventSource`（只支持 GET），需用 `fetch` + `ReadableStream` 读 SSE。
- 断在不同位置后果不同：断在断点处可续；断在流式中 / 工具执行中则本段回滚，用户重发该消息。

以上均已落到方案 2.5 / 2.7。

## 复盘：ADR-0001 决策 1 错在哪

1. **把实现当成了需求**：从「要双向传数据」直接跳到「需要双向协议」，漏掉中间一问——这些回传能不能拆成「独立的一次请求」。确认 / 提问由用户主动发起，可以。
2. **把「用户此刻就在等」当成了「服务端主动推」**：判断要不要长连接的标准只有一条——是不是「服务端要推用户此刻没在等的消息」（别人的新消息、异步任务完成通知）。是才需要长连接。
3. **拿「session 状态天然绑定连接」当优点**：这恰恰是问题本身——状态绑在连接上，断线就丢现场、换端就断。正确做法是状态放服务端，连接随便断。

**教训（选型自查清单）**：

- 需要用户输入的交互 ≠ 需要长连接；先问「这条回传能不能变成一次新请求」。
- 方案里一旦出现「粘性会话 / 心跳 / 重连 / 多实例广播」，先回头查是不是把状态放错了地方。
- 「某功能需要双向通信」不是结论，是待验证的假设——写下来，逐条证伪。
